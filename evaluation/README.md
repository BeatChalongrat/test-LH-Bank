# ผลการตรวจรับทางเทคนิคบนข้อมูลจำลอง

ผลหลังปรับการเรียกโมเดล รวมการทดสอบโหลดต่อเนื่องด้วยบัญชีจำลอง 5,000 บัญชี อยู่ใน [รายงานความจุและเวลาตอบ](capacity.md) ตารางด้านล่างบันทึกผลชุดติดตั้งก่อนเปลี่ยน inference

ทดสอบวันที่ 21 พฤศจิกายน 2026 ด้วยเอกสารไทย 8 ชิ้นและ threshold 0.42 โมเดลค้นคือ multilingual-E5-small ONNX แบบ quantized โมเดลเลือกหลักฐานคือ Qwen2.5-1.5B-Instruct Q4_K_M ผ่าน llama.cpp บน CPU

| ชุดคำถาม | ผลตรงเฉลย | หลักฐานที่ตรวจได้ |
|---|---|---|
| ชุดพัฒนา/ถดถอย 22 กรณี | 22/22 ทั้ง Windows และ Docker | ครอบคลุมแชตภาษาพูด เอกสารผิดสิทธิ์ การปฏิเสธ และข้อมูลไม่พอ ใช้ชุดนี้ระหว่างปรับระบบ [ผล Windows](regression-report.json) · [ผล Docker](docker-regression.json) |
| ชุดคำถามเพิ่มเติม 16 กรณี รอบแรก | 14/16 | โมเดลส่งต่อคำถามลาพักร้อนที่ตอบได้ และยกขั้นตอนเบิกเงินมาตอบกรณีหลักฐานชำระเงินหาย [ผลก่อนแก้](validation-firstpass.json) |
| ชุดเดิมหลังเพิ่มการตรวจหลักฐานที่ขาด บน Windows | 15/16 | กรณีหลักฐานชำระเงินหายส่งต่อได้ถูกต้อง เหลือการส่งต่อเกินจำเป็นเรื่องผู้อนุมัติพักร้อน [ผล Windows](validation-report.json) |
| ชุดเดิมบน Linux Docker ที่ส่งมอบ | 16/16 | ไฟล์น้ำหนักและ threshold เดียวกัน ตัวรัน llama.cpp ใน container เลือก HR-01 สำหรับคำถามผู้อนุมัติพักร้อน บน Windows ส่งต่อคำถามนี้ [ผล Docker](docker-validation.json) |

บนชุดเพิ่มเติม เอกสารคำตอบอยู่ในผลค้น 7/7 คำถามที่มีหลักฐาน (Recall@3 = 1.00) Precision@3 = 0.524 โดยหารด้วยจำนวนเอกสารที่คืนได้จริงไม่เกิน 3 แล้วเฉลี่ยต่อคำถาม หลังแก้ ระบบตอบเอง 6 จาก 7 คำถามที่ตอบได้บน Windows และ 7 จาก 7 บน Docker ทุกคำตอบเป็นข้อความที่ปรากฏในหลักฐาน โดยผู้ตรวจยังต้องประเมินว่าข้อความนั้นตอบคำถามครบและตรงบริบท การทดสอบนี้ตรวจข้อความและข้อเท็จจริงสำคัญหนึ่งจุดต่อคำถาม ตัวเลขดังกล่าวมีขนาดตัวอย่างเล็ก และรอบหลังแก้ใช้คำถามเดิม ต้องใช้ชุดปิดเฉลยใหม่จาก BU ก่อนตรวจรับทางธุรกิจ

## HTTP, ฐานข้อมูล และการปฏิบัติการ

- ทดสอบเว็บตั้งแต่ login → ถาม → เปิดหลักฐาน → ดูคลัง → ติดตามเคส ตรวจจอ desktop และ mobile
- ทดสอบฐาน Postgres 16 + pgvector 0.8.2 ด้วยบัญชี runtime ที่ไม่มี superuser/BYPASSRLS เมื่อยังไม่มี role ใน transaction จะอ่าน chunk ได้ 0 ส่วน employee และ reviewer อ่านได้ 7 ส่วน executive อ่านได้ 8 ส่วน
- ทดสอบการเปิดเคสจากบัญชีพนักงาน การห้ามพนักงานปิดเคส การปิดด้วย reviewer และการอ่านผลกลับ ทดสอบการเพิกถอนคีย์ การแยกแคชตามบทบาท/รุ่น และกรณี provider ขัดข้อง
- ทดสอบ OCR กับ PDF ที่มีเฉพาะภาพจริงใน container และตรวจข้อความกลับจากไฟล์นโยบายภาษาไทยทั้งสองไฟล์ สำรอง DB เป็น custom archive กู้ลงฐานใหม่ และตรวจว่ามีครบ 8 ส่วนในรุ่นที่เปิดใช้งาน

## ผลวัดโหลดผ่าน HTTP

ยิงผ่าน loopback เข้า Compose ที่ใช้ Postgres และ LLM จริงบนเครื่องพัฒนา เวลาวัดตั้งแต่เวลาที่กำหนดให้ส่งคำขอจนได้รับผล รวมการรอคิว

| โหลด | คำขอสำเร็จ | ผลวัด |
|---|---:|---|
| แคชอุ่น 3 คำถาม เป้า 20 ครั้ง/วินาที นาน 60 วินาที | 1,200/1,200 | cache hit ทั้งหมด, p50 33.65 ms, p95 71.64 ms, p99 102.93 ms [ผลวัด](warm-load.json) |
| โหลดผสม 30 คำถาม ส่งเข้า 2 ครั้ง/วินาที | 30/30 | hit 18 และ miss 12, p95 รวม 13.34 s, p95 ของ miss 15.25 s งานสุดท้ายเสร็จหลัง 28.75 s [ผลวัด](mixed-load.json) |

การตอบ HTTP สำเร็จใน benchmark ตรวจว่าระบบคืนสถานะ answered การวัดความถูกต้องของเนื้อหาใช้ชุดเฉลยแยกต่างหาก CPU inference หนึ่งช่องยังไม่ผ่านเป้าเวลาตอบ cold path ระดับองค์กร ให้ทดสอบที่อัตราพีก 18 ครั้ง/วินาทีด้วยสัดส่วน miss จริง หลังเพิ่ม capacity ตาม architecture

```shell
python scripts/load.py --rps 20 --count 1200 --out var/warm-load.json
python scripts/load.py --workload evaluation/mixed.json --rps 2 --count 30 --out var/mixed-load.json
```

เตรียม instance ทดสอบที่ใช้แคชใหม่สำหรับโหลดผสม ถ้ารันซ้ำภายใน TTL สัดส่วน hit จะเพิ่มขึ้น ให้ดูค่า cache_hits ในรายงานทุกครั้ง
