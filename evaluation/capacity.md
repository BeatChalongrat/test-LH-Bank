# เวลาตอบของระบบเมื่อใช้คำถามใหม่ผสมกับคำถามซ้ำ

## ผลหลังปรับช่วงพีก · 22 พฤศจิกายน 2026

จำลอง 5,000 บัญชี ถามผ่านหน้าแชตที่บันทึกประวัติ ฐานโหลด 50,000 คำถามใน 8 ชั่วโมงเฉลี่ย 1.74 ครั้ง/วินาที เลือกพีก 18 ครั้ง/วินาทีประมาณ 10 เท่าของค่าเฉลี่ยในเวลางาน ยิงต่อเนื่อง 30 นาที แคช 60% อีก 40% เป็นคำถามใหม่ที่สลับบริบทจาก 8 เอกสาร ตั้งเวลาส่งแบบ open-loop และนับเวลารอฝั่งผู้ยิงเข้า latency ทุกคำขอ การนับว่าถูกต้องตรวจทั้งข้อเท็จจริง สถานะ และเอกสารอ้างอิง

| รอบ · 18 ครั้ง/วินาที | คำขอ | p95 รวม (วิ.) | คำถามใหม่ (วิ.) | แคช (วิ.) | ถูกพร้อมหลักฐาน | ถูกภายใน 3 วิ. |
|---|---:|---:|---:|---:|---:|---:|
| [CPU ก่อนปรับ](chat-peak.json) | 5,000 | 16.87 | 21.34 | 14.63 | 3,123 | 2,216 |
| หลังปรับ 5,000 คำขอแรกของรอบต่อเนื่อง | 5,000 | 9.40 | 11.46 | 0.23 | 4,562 | 3,127 |
| [หลังปรับ ครบ 30 นาที](peak-soak.json) | 32,400 | 9.74 | 11.93 | 0.24 | 28,886 | 19,578 |

**ผลต่อการเปิดใช้** p95 รวม 9.74 วินาที เทียบกับเป้า 3 วินาที ตอบถูกพร้อมหลักฐาน 28,886/32,400 และถูกภายใน 3 วินาที 19,578 (60.4%) ในรอบเดียวกันมี cache hit จริง 19,440 ครั้ง คิว inference เต็มจนส่งต่อ 3,514 ครั้ง รายงาน JSON แยก HTTP status เหตุผล และจำนวน trace ที่จับคู่ได้ [ผลรวม](peak-soak.json) · [ผลรายคำขอบีบอัด](peak-soak.jsonl.gz)

**สิ่งที่เปลี่ยน** แยกคำนวณ embedding ออกจากช่วงถือ connection ลดรอบติดต่อฐานข้อมูลเมื่อเปิดแชต ตรวจการคืนสิทธิ์เข้า inference เมื่อถึง timeout และกระจายงานไป replica ที่ว่าง ทดสอบระหว่างทางบน CPU ด้วย 5,000 คำขอแรกของรอบวินิจฉัยที่ยุติภายหลัง ได้ p95 14.41 วินาที ตอบถูก 3,132 ข้อ [ผลระหว่างทาง](peak-retune-5000.json) · [ข้อมูลรายคำขอ](peak-retune-5000.jsonl.gz)

รอบสุดท้ายใช้ API 2 worker, DB pool 8 + overflow 8 ต่อ worker, inference พร้อมกัน 4 งานต่อ worker, admission timeout 8 วินาที ตัวรันโมเดลหลักบน Docker CPU และ replica ที่สองบน Windows ผ่าน Vulkan ใช้เครื่องเดียวกัน (Ryzen AI 7 445, Radeon 840M, 12 logical processors) ทั้งสองใช้ Qwen Q4 เดียวกันอย่างละ 4 slots โมเดลและดัชนีโหลดพร้อมก่อนเริ่ม รอบนี้เปลี่ยนทั้ง topology และตัวส่งโหลด จึงแยกผลประหยัดเวลารายการปรับแต่ละข้อจากตัวเลขรวมไม่ได้

**อ่าน trace** ความล่าช้าของการเริ่มส่งเทียบกำหนด p95 1.13 ms, เวลารอสิทธิ์เข้า inference p95 8.00 วินาที และเวลาเรียก LLM ผ่าน HTTP ของงานที่ผ่านถึงขั้นนั้น p95 8.05 วินาที ตัวนับงาน LLM ที่มี trace จบแยกตาม replica คือ CPU 2,189 และ Vulkan 3,116 ค่า percentile ของแต่ละช่วงมาจากประชากรต่างกัน

**ขั้นถัดไป** แยก inference ออกจาก API/DB บนเครื่องเฉพาะ วัด throughput ต่อ replica ที่ยังผ่าน p95 cold ≤3 วินาที จัดจำนวน replica สำหรับ 7.2 cold requests/s พร้อม headroom 30% และสำรองหนึ่งชุด แล้วทดสอบซ้ำทั้งระบบด้วย traffic ของ BU การเปิดให้พนักงาน 5,000 คนต้องพิจารณาผลพีกและงานส่งต่อพร้อมกัน

### ทำซ้ำบน Windows พร้อม Vulkan

ติดตั้งตาม README ให้สแตกหลักพร้อมใช้งาน ลง dependencies จาก `requirements-dev.txt` สำหรับเครื่องยิงโหลด เปิด PowerShell ในโฟลเดอร์ที่ clone แล้วใช้หน้าต่างแรกสำหรับสำเนาโมเดลที่สอง

```powershell
python scripts/models.py --llm --windows-vulkan
.\models\vulkan\llama-server.exe -m models/qwen.gguf --host 127.0.0.1 --port 18768 --parallel 4 --ctx-size 8192 --threads 2 --threads-batch 3 -ngl 99 --alias knowledge-local
```

ใน PowerShell หน้าต่างที่สอง ตั้งค่าด้านล่างสำหรับสแตก benchmark ซึ่งมีฐานข้อมูลและบัญชีแยกจากพอร์ทัลหลัก บนเครื่องทดสอบ Docker Desktop เข้าถึง replica ผ่าน host.docker.internal

```powershell
$env:API_WORKERS = '2'
$env:INFERENCE_IN_FLIGHT = '4'
$env:LLAMA_EXTRA_URL = 'http://host.docker.internal:18768/v1'
$env:LLAMA_EXTRA_SLOTS = '4'
docker compose -p folio-capacity -f compose.yaml -f evaluation/capacity.compose.yaml up -d --build --wait api
python -m evaluation.capacity --chat --rps 18 --count 32400 --out var/capacity/peak-soak.json
docker compose -p folio-capacity -f compose.yaml -f evaluation/capacity.compose.yaml stop api db
```

ไฟล์ JSON อ้าง SHA-256 ของ JSONL ก่อนบีบอัด สคริปต์คืน exit code 1 เมื่อผลต่ำกว่าเกณฑ์และยังคงบันทึกผลไว้ครบ


## ผลวัดหน้าแชต วันที่ 22 พฤศจิกายน 2026

ยิงคำถามผ่าน HTTP ไปยัง `POST /api/conversations/{id}/messages` เปิดบทสนทนาใหม่หนึ่งรายการต่อคน รวมเวลาตั้งแต่เวลาที่กำหนดให้ยิงคำขอจนได้คำตอบที่บันทึกลง PostgreSQL ใช้คำถามตามระเบียบและแชตจำลอง 8 เอกสาร แคชคำตอบ 60% คำถามใหม่ 40% ใช้ดัชนีและบริการโมเดลที่พร้อมทำงานแล้ว รอบนี้วัดเส้นทางถามความรู้ ส่วนการถามต่อ เรียกเครื่องมือตรวจเคส การแยกสิทธิ์หน้าผู้ดูแล และการส่งต่อทดสอบแยกใน Chromium

| รอบ | คำถาม/วินาที | บัญชี | p95 รวม (วิ.) | p95 คำถามใหม่ (วิ.) | p95 แคช (วิ.) | ตรงเฉลยและอ้างอิงถูก | ตรงเฉลยใน 3 วิ. |
|---|---:|---:|---:|---:|---:|---:|---:|
| [ชั่วโมงทำงาน](chat-office.json) | 2 | 180 | 0.88 | 1.21 | 0.12 | 180/180 | 180 |
| [ช่วงพีก](chat-peak.json) | 18 | 5,000 | 16.87 | 21.34 | 14.63 | 3,123/5,000 | 2,216 |

รอบพีกส่งครบ 5,000 คำขอ เหตุผลใน trace ได้แก่ evidence = 3,123, inference_overloaded = 1,874, generator_unavailable = 3 คำตอบ fallback นับเป็นคำตอบที่พลาดเมื่อเฉลยมีหลักฐานครบ เครื่องเดียวจึงยังไม่ผ่าน SLO ช่วงพีกก่อนเปิดให้พนักงานทั้งองค์กร ตัวเลขนี้มาจากโหลดสังเคราะห์แบบ open-loop คนละหนึ่งคำถาม ระยะยิงรอบพีกประมาณ 4.6 นาที ผล soak test 30 นาทีหลังปรับอยู่ในตารางด้านบน ส่วนการตรวจรับด้วยข้อมูลของ BU ต้องวัดบนชุดที่ BU ถือเฉลย

Trace รอบพีกบันทึกเวลารอเข้า inference ที่ p95 8.29 วินาที และเวลาเรียก LLM ที่ p95 14.12 วินาที ขณะเดียวกันคำขอที่พบแคชมี p95 ปลายทางถึงปลายทาง 14.63 วินาที รอบนี้ยังไม่ได้แยกเวลารอ connection pool และเวลาธุรกรรมแชตแต่ละช่วง การทดสอบขยายระบบควรแยกวัดขั้นตอนเหล่านี้พร้อมการเพิ่มกำลัง inference แล้วตรวจทั้งคำตอบที่ถูกและคำตอบที่ทันเวลา

รันทวนบนสแตกแยกตามขั้นตอนด้านล่าง โดยเพิ่ม `--chat` เช่น `python -m evaluation.capacity --chat --rps 18 --count 5000 --out evaluation/chat-peak.json` เก็บผลรายคำขอโดยใช้หมายเลขผู้ใช้สังเคราะห์และ trace ID [ชั่วโมงทำงาน](chat-office.jsonl.gz) · [ช่วงพีก](chat-peak.jsonl.gz)

รอบทำงานมี 1,195/1,200 คำถามที่ทั้งตรงเฉลยและเสร็จภายใน 3 วินาที คำถามใหม่ 480 ข้อแยกเป็น XLM-R ตอบจากหลักฐานได้ 216 ข้อและ Qwen เลือกหลักฐาน 264 ข้อ p95 ของเวลารอเริ่มงานเพียง 0.35 ms รอบพีกมี 3,025/5,000 คำถามที่ทั้งตรงเฉลยและเสร็จใน 3 วินาที จากคำถามใหม่ 2,000 ข้อ มี 816 ข้อที่ตอบได้ อีก 1,168 ข้อรอคิวเกินกำหนด และ 16 ข้อเรียกโมเดลไม่สำเร็จ ระบบคืน HTTP 200 ทั้ง 5,000 ครั้ง รวมทั้งคำตอบส่งต่อ

รอบพีกใช้ 5,000 บัญชีคนละหนึ่งคำถาม ยิงเข้า 18 ครั้ง/วินาทีประมาณ 4 นาที 38 วินาที และใช้รวม 4 นาที 53 วินาทีจนได้คำตอบสุดท้าย p95 ของการรอเข้าประมวลผลอยู่ที่ 8.00 วินาที และ p95 ของการเรียก Qwen ที่สำเร็จอยู่ที่ 18.20 วินาที เทียบกับ p95 ของการค้นเอกสาร 0.116 วินาที แต่ละค่าเป็นเปอร์เซ็นไทล์ของคนละช่วงงาน นำมาบวกตรง ๆ ไม่ได้ หากจะรับพีกนี้ ให้แยก inference ไปเครื่องที่เพิ่มกำลังได้ แล้ววัดการรองรับคำถามใหม่อย่างน้อย 7.2 ครั้ง/วินาทีภายใต้เกณฑ์เดิมก่อนรันโหลดผสม 18 ครั้ง/วินาทีเป็นเวลา 30 นาที

ทุกค่าของ p95 วัดจากเวลาที่กำหนดให้ส่งคำถามจนผู้เรียกได้รับคำตอบครบ รวมเวลารอคิว การค้น การตรวจสิทธิ์ การเรียกโมเดลและการบันทึกผล ใช้ nearest-rank และรวมเวลาของคำขอที่ส่งต่อด้วย ตัวเลขแถวก่อนและหลังปรับชุดสั้นใช้คำถาม 30 รายการตามลำดับเดิม ผ่านเมื่อ API คืนคำตอบ ส่วนสองรอบต่อเนื่องตรวจสถานะ เอกสารตามสิทธิ์ และข้อเท็จจริงที่คาดหวังครบทุกคำขอ

ข้อมูลรายคำขอมีลำดับการส่ง หมายเลขบัญชีจำลอง สถานะแคช ระยะเวลา trace ID และผลตรวจคำตอบ ค่า SHA-256 ของไฟล์หลังคลาย gzip อยู่ในช่อง `trace_log_sha256` ของรายงานแต่ละรอบ [รายการรอบทำงาน](capacity-office.jsonl.gz) · [รายการรอบพีก](capacity-peak.jsonl.gz)

หลังติดตั้ง image ที่ส่งมอบ ทดสอบซ้ำกับโมเดลจริงและชุดตรวจสิทธิ์ การปฏิเสธ การส่งต่อ เอกสารแชต และคำถามนโยบาย ได้ 22/22 กับ 16/16 ผลรายข้อทั้งสองไฟล์ตรงกับการประเมินรุ่นเดิมทุกไบต์ ทั้งสองชุดใช้ซ้ำระหว่างพัฒนา การประเมินความแม่นยำกับคำถามใหม่จากพนักงานจริงเป็นขั้นตอน UAT ของ BU [ชุดถดถอย 22 ข้อ](docker-regression.json) · [ชุดเพิ่มเติม 16 ข้อ](docker-validation.json)

## โหลดและเงื่อนไขที่ใช้ตีความ

- 50,000 คำถามใน 8 ชั่วโมงเฉลี่ย 1.74 ครั้ง/วินาที ทดสอบที่ 2 ครั้ง/วินาที ส่วนพีก 18 ครั้ง/วินาทีมาจากสมมติฐานประมาณสิบเท่าของค่าเฉลี่ยช่วงทำงาน เมื่อพบแคช 60% พีกนี้ต้องรับคำถามใหม่ 7.2 ครั้ง/วินาที
- เปิด API ผ่าน HTTP บน Docker Desktop และ CPU AMD Ryzen AI 7 445 จำนวน 6 คอร์ 12 เธรด Docker เห็นหน่วยความจำ 11.68 GiB ใช้ PostgreSQL/pgvector, E5 ONNX, XLM-R reader และ Qwen2.5-1.5B Q4_K_M ผ่าน llama.cpp หนึ่งเครื่อง สี่ช่องประมวลผล ทุกคำถามผ่านการยืนยันตัวตนจริงด้วยคีย์ของบัญชีจำลอง
- แยก API ฐานข้อมูล และแคชทดสอบจากระบบหลัก ใช้เซิร์ฟเวอร์โมเดลเดียวกับระบบหลัก ตั้งเวลาเปิดคำขอแบบ open-loop ล่วงหน้า สุ่มโดยกำหนด seed 6407 โหลดจึงเข้าต่อแม้บางคำตอบยังไม่กลับ แต่ละชุดมีคำถามซ้ำ 60% และคำถามใหม่ 40% เปิดแคชคำถามซ้ำแยกตามสิทธิ์ก่อนเริ่มจับเวลา คำถามใหม่หมายถึงไม่พบในแคชคำตอบ โดยตัวโมเดลโหลดอยู่ในหน่วยความจำแล้วและสามารถใช้ prefix จากคำถามก่อนหน้า
- คลังมี 8 เอกสาร แคชอุ่นมีคำถามเรื่องการเบิก การลา สถานะเคส และข้อมูลผู้บริหาร คำถามใหม่สร้างจาก 12 รูปแบบเรื่องนโยบายการเบิกและการลา โดยเปลี่ยนวัน จำนวนเงิน สถานที่ หรือช่วงลา จำลองบัญชีพนักงาน 4,850 บัญชี ผู้ตรวจ 100 บัญชี และผู้บริหาร 50 บัญชี ความหลากหลายของเอกสาร ความยาวคำถาม สัดส่วนแคช และเวลาเครือข่ายขององค์กรจริงอาจเปลี่ยนผล
- เกณฑ์ผ่านรอบต่อเนื่องกำหนดให้ p95 รวมและคำถามใหม่ ≤3 วินาที แคช ≤250 ms ทุกคำขอที่มีเฉลยต้องตอบได้ตรงแหล่งอ้างอิงและข้อเท็จจริง ต้องจับคู่ trace ได้ครบ และสัดส่วนแคชที่เกิดจริงต้องตรงแผน HTTP 200 ที่เป็นการส่งต่อถือว่าพลาดในชุดโหลดนี้

## สิ่งที่เปลี่ยนในเส้นทางของคำถามใหม่

1. ให้เอกสารที่ผู้ถามมีสิทธิ์อ่านอยู่ต้น prompt เรียงตามรหัส นำส่วนที่โมเดลประมวลผลไว้มาใช้ซ้ำได้ โมเดลเลือกรหัสเอกสารหรือส่งต่อ หากโทเคนแรกระบุรหัสได้แน่ชัดก็จบการสร้างคำตอบทันที หากหลายรหัสขึ้นต้นเหมือนกันต้องได้รหัสเต็ม เซิร์ฟเวอร์คืนข้อความจากเอกสารต้นฉบับ [llama.cpp server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
2. ใช้โมเดลอ่านหลักฐาน XLM-R กับคำถามข้อเท็จจริงเมื่อพบนโยบายพนักงานที่มีคะแนนนำชัดเจน ส่งคำถามต่อให้ Qwen เมื่อคะแนนช่วงข้อความเทียบกับคะแนนไม่มีคำตอบต่างกันต่ำกว่า 4 หรือเป็นคำถามขั้นตอน ข้อยกเว้น แชต หรือเอกสารผู้บริหาร ค่า 4 เป็นเกณฑ์ของตัวเลือกหลักฐาน ต้องวัดซ้ำกับภาษาไทยของแต่ละองค์กร [XLM-R SQuAD2 distilled](https://huggingface.co/deepset/xlm-roberta-base-squad2-distilled)
3. แยกจำนวนงาน inference ที่ทำพร้อมกันจากการอ่านแคชและการยืนยันตัวตน เมื่อรอเข้าประมวลผลเกิน 8 วินาทีให้เปิดเคส เก็บเหตุผล `inference_overloaded` และแจ้งผู้ถามว่ามีผู้ใช้งานจำนวนมาก ตั้งค่าคิวด้วย `INFERENCE_IN_FLIGHT` และ `INFERENCE_QUEUE_TIMEOUT` ดูเวลาแต่ละช่วงได้จาก trace

## รันซ้ำ

เริ่มระบบหลักและติดตั้ง Python dependencies ตาม README ก่อน เลือกเวลาที่ไม่มีการใช้งานตัวรันโมเดลหลักเพื่อให้ผลเทียบกันได้ ใช้ Docker Compose ที่รองรับ `!override` สำหรับสแตกทดสอบ หากใช้โมเดล llama.cpp ที่เครื่องอื่นให้ตั้ง `BENCH_LLM_BASE_URL` เป็นปลายทางที่ container เข้าถึงได้

```shell
docker compose -p folio-capacity -f compose.yaml -f evaluation/capacity.compose.yaml up -d api
python -m evaluation.capacity --rps 18 --count 5000 --out var/capacity/peak.json
python -m evaluation.capacity --rps 2 --count 1200 --out var/capacity/office.json
docker compose -p folio-capacity -f compose.yaml -f evaluation/capacity.compose.yaml stop api db
```

รันทีละรอบ เครื่องมือเริ่มจากแคชคำตอบว่างในฐาน `capacity` และเปิดแคชตามแผน แต่ละรอบเขียน JSON สรุปกับ JSONL รายคำขอใน `var/capacity/` รวมเวลาเข้าคิว เหตุผลที่ตอบหรือส่งต่อ และ trace ID คืน exit code 1 เมื่อพลาดเกณฑ์ใดเกณฑ์หนึ่ง ใช้ `--count 32400 --rps 18` สำหรับ UAT พีก 30 นาทีหลังจัดสรรเครื่อง inference ตามปริมาณงานจริง

หากต้องการเทียบกับ baseline 30 คำถาม ให้เปิดสแตกทดสอบด้านบนแล้วรันสองคำสั่งนี้ก่อนหยุดสแตก คำสั่งแรกคืนแคชในฐาน benchmark ให้เป็นสถานะเริ่มต้น

```shell
docker compose -p folio-capacity -f compose.yaml -f evaluation/capacity.compose.yaml exec -T db psql -U desk_owner -d capacity -c "TRUNCATE answers"
python scripts/load.py --base http://127.0.0.1:18770 --credentials var/capacity/identities.json --workload evaluation/mixed.json --rps 2 --count 30 --out var/capacity/comparable.json
```
