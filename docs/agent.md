# แชตผู้ช่วยพนักงานและหน้าผู้ดูแล AI

## เปิดใช้งาน

| ผู้ใช้ | วิธีเข้าใช้งาน | สิ่งที่ทำได้ |
|---|---|---|
| พนักงาน | [หน้าแชต](http://127.0.0.1:8765/#ask) หรือเปิด `open-workspace.cmd` แล้วเลือก **แชตผู้ช่วย AI** ที่แถบเมนูบริการ | ส่งคำถาม เปิดหลักฐาน ถามต่อ เริ่มแชตใหม่ เปิดประวัติ และตรวจเคสของตน |
| ผู้ดูแล AI | [หน้าผู้ดูแล](http://127.0.0.1:8765/admin) หรือเปิด `open-admin.cmd` บนเครื่องที่มีสิทธิ์จัดการ Docker | ดูโมเดล รุ่นดัชนี เกณฑ์คะแนน ผลการตอบและสาเหตุใน 24 ชั่วโมง เปิด/ปิดเครื่องมือตรวจเคส ดูประวัติการตั้งค่า และอัปโหลดเอกสารพร้อมระบุสิทธิ์ตามบทบาท แผนก และรายบุคคล |
| เจ้าหน้าที่สนับสนุน | เมนูเรื่องรอเจ้าหน้าที่ดูแลด้วยบทบาท reviewer | รับเคสพนักงาน ตรวจหลักฐาน บันทึกคำตอบ และปิดเคส |
| ผู้บริหาร | เข้าด้วยบทบาท executive | ค้นเอกสารสำหรับผู้บริหารและจัดการคิวผู้บริหารตามสิทธิ์ |

บนระบบองค์กร ใช้ SSO และตั้ง `OIDC_GROUP_ADMIN` เป็นกลุ่มผู้ดูแล AI แยกจากกลุ่มอื่น บัญชีที่อยู่หลายกลุ่มใช้บทบาทเดียวตามลำดับ admin → executive → reviewer → employee หน้าผู้ดูแลแสดงผลรวมและการตั้งค่า ส่วนเอกสารค่าตอบแทนมีสิทธิ์อ่านเฉพาะ executive บนเครื่องที่เปิด local authentication ตัวเปิดสองไฟล์สร้างคำเชิญอายุ 10 นาทีให้บัญชีรายบุคคลแยกกัน การสลับบัญชีในเบราว์เซอร์เดียวกันจะเปลี่ยนเซสชันของพอร์ทัล

## ลองบทสนทนา

1. พิมพ์ **ค่าแท็กซี่เบิกได้สูงสุดกี่บาทต่อเที่ยว** เปิดอ้างอิง FIN-01 เพื่อตรวจวงเงิน 600 บาทในระเบียบจำลอง
2. ถามต่อ **แล้วต้องยื่นภายในกี่วัน** ผู้ช่วยใช้ชื่อเอกสารที่อ้างในคำตอบล่าสุดมาช่วยค้นใหม่ ตรวจสิทธิ์และให้หลักฐานสำหรับกำหนด 15 วันปฏิทิน คำถามที่ระบุหัวข้อใหม่จะค้นตามคำถามใหม่
3. พิมพ์ **บริษัทมีสวัสดิการค่าเล่าเรียนบุตรไหม** เมื่อหลักฐานไม่พอ ผู้ช่วยส่งให้เจ้าหน้าที่และให้ปุ่มติดตามเรื่องนี้ พิมพ์ **สถานะเคสนี้** เพื่อตรวจเลขเคสจากคำตอบล่าสุด หรือ **ดูเคสของฉัน** เพื่ออ่านยอดตามสถานะ ณ เวลาที่ถาม
4. ที่หน้าผู้ดูแล เปิดดูจำนวนคำตอบ การส่งต่อและการปฏิเสธ การปิดเครื่องมือตรวจเคสมีผลกับคำขอตรวจเคสครั้งถัดไป การตัดสินว่าคำตอบถูกต้องต้องเทียบเฉลยและตรวจเนื้อหา

## ต่อ LLM ขององค์กร

ค่าเริ่มต้นคือ Qwen2.5-1.5B-Instruct Q4 ผ่าน llama.cpp ในเครือข่าย Docker หากใช้ gateway ขององค์กร ให้เลือก deployment ที่รองรับ Chat Completions และ structured output แบบ JSON Schema strict สำหรับ `choice` ซึ่งรับได้เฉพาะรหัสหลักฐานหรือ `NONE` กำหนดค่าด้านล่างฝั่งเซิร์ฟเวอร์ แล้วเรียก `docker compose up -d --no-deps api`

```dotenv
LLM_PROTOCOL=openai
LLM_BASE_URL=https://your-approved-gateway.example/v1
LLM_MODEL=your-deployment-id
LLM_REVISION=your-deployment-version
```

ส่ง `LLM_API_KEY` ผ่าน secret ของ deployment เมื่อ gateway ต้องใช้ bearer token เปลี่ยน `LLM_REVISION` เมื่อเปลี่ยนรุ่นโมเดลเพื่อแยก cache เส้นทางนี้ส่งคำถามและข้อความจากเอกสารที่ผู้ใช้มีสิทธิ์ไปยัง gateway ที่ตั้งค่า จึงต้องเลือกปลายทางตามการจัดชั้นข้อมูลที่องค์กรอนุมัติ เก็บคีย์ไว้ฝั่ง API ทุกครั้ง หลังสลับ provider ให้รันชุดเฉลยและทดสอบโหลดกับ deployment นั้นอีกครั้ง [ตัวเชื่อมโมเดล](../knowledge/service.py) · [ตัวแปร Compose](../compose.yaml)

## การดูแลบทสนทนา

ข้อความและเคส fallback บันทึกในธุรกรรมเดียว การส่งซ้ำด้วย turn ID และ payload เดิมคืนผลเดิม การเขียนทับจากอีกแท็บให้ HTTP 409 ข้อมูลแชตค้นตามบัญชี บทบาท และรุ่นดัชนีที่ใช้งาน หน้าเว็บแสดงได้ถึง 50 บทสนทนาและ 50 ข้อความผู้ใช้ล่าสุดต่อบทสนทนา แชตที่ไม่มีการใช้งานมา 30 วันหมดสิทธิ์แสดง ให้ตั้งงาน `python -m knowledge prune` เพื่อกำจัดข้อมูลที่หมดอายุ ตรวจ trace รายคำตอบได้ผ่าน `python -m knowledge trace TRACE_ID` ในคอนเทนเนอร์ seed [คู่มือปฏิบัติการ](operations.md)

หน้าแชตใช้ `POST /api/conversations/{id}/messages` พร้อม UUID สำหรับบทสนทนาและ turn ID ส่วน parent ID คือข้อความล่าสุดสำหรับการถามต่อ โปรแกรมเดิมเรียก `POST /api/ask` ได้ ดูรายการ API ใน [OpenAPI ของเครื่องที่ติดตั้ง](http://127.0.0.1:8765/docs)

สำหรับการเรียกทั้ง embeddings และ chat ผ่าน API รวมขั้นตอนย้ายดัชนีและจำกัดคิว ดู [คู่มือ provider](provider.md)
