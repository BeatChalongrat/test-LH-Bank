# คู่มือ D2 Operation

## เจ้าของงานและขอบเขต

ทีม Platform ดูแล API, Postgres, ดัชนีและ inference ฝ่าย HR/Finance เป็นเจ้าของข้อความนโยบาย ทีม Service Desk เปิดคิว **งานสนับสนุน** ด้วยบัญชี reviewer สำหรับคำถามพนักงาน ผู้บริหารดูแลคิวที่จำกัดเฉพาะ executive การปิดเคสต้องบันทึกผลตรวจ ชื่อเอกสารที่ใช้หรือผู้ยืนยัน ผู้ถามจะเห็นผลในหน้าเดิม ระบบไม่มีเครื่องมืออนุมัติจ่ายเงินหรือแก้สิทธิ์พนักงาน

## ตรวจบริการและหาสาเหตุ

```shell
docker compose ps -a
docker compose logs --since 15m api llm
docker compose --profile monitoring up -d
```

เปิด Prometheus ที่ http://127.0.0.1:8767/targets และดู Alerts ที่ /alerts ตัว scraper ใช้ service token สำหรับ metrics โดยเฉพาะ ชุดส่งมอบประเมิน alert rules ในเครื่อง ให้ผูก Alertmanager และผู้รับเวรของลูกค้าก่อนเปิดใช้งานจริง

| อาการ | ตรวจอะไร | วิธีคืนบริการ |
|---|---|---|
| API ไม่พร้อม | `/health/live` ตรวจ process และ `/health/ready` ตรวจฐานข้อมูลกับรุ่นดัชนี ดูสถานะ seed ซึ่งจบงานด้วย exit 0 ตามปกติ | กู้ DB ก่อน รัน seed ใหม่จาก catalog ที่ตรวจแล้ว readiness ยังคงตอบได้เมื่อ LLM ขัดข้องเพื่อให้เปิดคลังและรับเคสได้ |
| ส่งต่อเพิ่มอย่างรวดเร็ว | แยก `insufficient_evidence` จาก `generator_unavailable` ใน metrics และ trace ตรวจ container health ของ llm และเวลารอ | กรณีโมเดลขัดข้อง ตรวจ checksum และหน่วยความจำก่อน restart llm ให้ reviewer รับเคสค้าง กรณีคะแนนต่ำให้เจ้าของเอกสารตรวจภาษา รุ่น และช่องว่างในระเบียบ |
| คำตอบช้าช่วงพีก | ตรวจ `inference_overloaded` ใน metrics แล้วเปิด trace เทียบเวลารอ `admission_ms` เวลาค้น `retrieval_ms` เวลาของ reader `reader_ms` และเวลาเรียก Qwen รวมคิวโมเดล `llm_http_ms` | หากแคชยังเร็วแต่คิวโมเดลเต็ม ให้เพิ่มเครื่อง inference และทดสอบซ้ำด้วยสัดส่วน hit/miss ที่วัดได้ในองค์กร ดู [วิธีวัดความจุ](../evaluation/capacity.md) |
| คำตอบผิดหรือเอกสารคนละสิทธิ์ | รับ trace ID และเวลาจากผู้ใช้ ดูบทบาท รุ่นดัชนีและ ref ห้ามนำเนื้อหาผู้บริหารลงช่อง incident ทั่วไป | กรณีรั่วให้จำกัดเส้นทางที่ได้รับผลทันที เก็บ log แบบจำกัดสิทธิ์ ตรวจ ACL ของ **รุ่นปัจจุบัน** ก่อนสลับรุ่น ไล่ผลที่เคยส่งออก ประสาน Security และเจ้าของข้อมูล เปิดใหม่เมื่อทดสอบข้ามสิทธิ์ผ่าน |

หากตรวจเคสผ่านแชตไม่ได้ ให้ผู้ดูแล AI เปิด /admin ตรวจสถานะเครื่องมือและชื่อผู้เปลี่ยนล่าสุด เมื่อแก้สาเหตุแล้วเปิดเครื่องมือกลับและตรวจจากบัญชีพนักงานด้วยคำถาม **ดูเคสของฉัน** ผู้ดูแลใช้กลุ่ม OIDC_GROUP_ADMIN สำหรับคอนโซลนี้ [ขั้นตอนและขอบเขตสิทธิ์](agent.md)

ค้นเหตุการณ์หนึ่งรายการโดยแทน `TRACE_ID` ด้วยเลขที่หน้าเว็บแสดง

```shell
docker compose run --rm --no-deps seed python -m knowledge trace TRACE_ID
```

Trace มีเวลาค้นและสร้าง เหตุผล คะแนน รุ่น และแหล่งอ้างอิง การแจ้งเตือนของ Prometheus อยู่ใน `deploy/alerts.yml` ทีมเวรควรติดตาม cache hit, provider errors, p95 และอายุคิว ตรวจตัวอย่างคำตอบร่วมกับ BU ทุกสัปดาห์ การปกปิดข้อความในคิวครอบคลุมรูปแบบอีเมล เบอร์และคีย์บางประเภท ข้อความอิสระอาจมีชื่อหรือข้อมูลส่วนบุคคลตกค้าง ให้จำกัดผู้เห็นและทบทวน retention กับลูกค้า

## อัปโหลดเอกสารและกำหนดสิทธิ์

บัญชี admin เปิด `/admin` → **เอกสารสำหรับผู้ช่วย AI** ระบุไฟล์ ชื่อ และเจ้าของเรื่อง เลือกผู้มีสิทธิ์ตามบทบาท แผนก หรือรายบัญชี ผู้ใช้จะเห็นเอกสารเมื่อเข้าตามสิทธิ์ที่เลือกอย่างน้อยหนึ่งรายการ ถ้าต้องการจำกัดเฉพาะ HR ให้เลือก HR ช่องเดียว ผู้ดูแลจัดการสิทธิ์และข้อมูลรายการได้ ส่วนการอ่านเนื้อหาและดาวน์โหลดใช้เงื่อนไขเดียวกับพนักงาน

เพิ่มรหัสแผนกและผูกบัญชีใน **จัดการแผนก** รายชื่อใช้บัญชีท้องถิ่นที่เปิดใช้งานและบัญชีองค์กรที่เคยเข้าสู่ระบบผ่าน SSO แผนกและสมาชิกบริหารในพอร์ทัล การเปลี่ยนสมาชิกมีผลหลังบันทึกโดยใช้เซสชันเดิมได้

รองรับ PDF (OCR ไทยและอังกฤษสำหรับหน้าสแกน), DOCX (ข้อความรวมตาราง), XLSX (ค่าที่บันทึกในเซลล์ตามชีต), PPTX (ข้อความตามสไลด์), TXT, Markdown และ CSV ขนาดไฟล์สูงสุด 15 MB ส่วน PDF สูงสุด 80 หน้า รองรับข้อความ UTF‑8 และ UTF‑16 ที่มี BOM หากอ่านไม่ได้ให้แก้ไฟล์แล้วส่งใหม่ เมื่อขึ้น **พร้อมใช้ในแชต** จึงเริ่มค้นและดาวน์โหลดได้

ไฟล์ต้นฉบับ คิวจัดทำดัชนี สิทธิ์ และประวัติการแก้ไขอยู่ใน PostgreSQL ตัว `indexer` ประมวลผลคิว ให้ใช้ `docker compose logs --since 15m indexer` หากรายการค้าง เมื่อ worker หยุดกลางงาน งานจะกลับเข้าคิวเมื่อ lease หมดอายุภายใน 10 นาที

สิทธิ์ชุดเดียวคุมการค้นก่อนส่งข้อมูลให้โมเดล คลังเอกสาร และการดาวน์โหลด โดยมี PostgreSQL RLS กรองอีกชั้น แยกแคชตามบัญชีเมื่อใช้สิทธิ์รายบุคคลหรือแผนก การเปลี่ยนสมาชิกหรือสิทธิ์จะเปลี่ยนรุ่นของแคชและประวัติแชต กด **แก้ไขสิทธิ์** เพื่อหยุดเผยแพร่ เอกสารเดิมจาก catalog ยังคงใช้สิทธิ์ตาม audience ที่กำหนดไว้

## เปลี่ยนเอกสาร ย้อนรุ่น และดูแลข้อมูล

เมื่อส่งต่อคำถาม ระบบเก็บรหัสเอกสารที่อัปโหลดและผู้ถามเข้าถึงได้ในขณะนั้นไว้กับเคส ผู้ที่จะอ่านประวัติ รับ คืน หรือปิดเคสต้องมีสิทธิ์อ่านเอกสารเหล่านั้นครบตามสิทธิ์ปัจจุบัน รวมถึงอยู่ในบทบาทที่รับคิวนั้นได้ หากสิทธิ์ผู้รับงานถูกถอน ให้เจ้าของข้อมูลและ D2 ตรวจเลขเคสและมอบหมายผู้มีสิทธิ์ผ่านกระบวนการขององค์กร การอัปเกรดฐานเดิมจะจำกัดเคสเก่าตามเอกสารที่บทบาท reviewer ไม่มีสิทธิ์โดยตรง เพราะเคสรุ่นเดิมไม่มีประวัติสิทธิ์ ณ วันที่เปิด

ตรวจ `knowledge_inference_slots_available` และ `knowledge_inference_waiters` พร้อมเวลารอ admission, embedding, การรอ connection ฐานข้อมูล และเวลา LLM ใน trace ตัววัดปลายทางสำหรับ SLO คือเวลาจากเครื่องส่งโหลดจนถึงคำตอบแชตที่บันทึกสำเร็จ กรณีคำถามใหม่ทั้งหมดส่งต่อแม้โมเดลว่าง ให้ตรวจการคืนช่องประมวลผลหลังคำขอหมดเวลารอ

1. นำไฟล์เข้าพื้นที่ staging ให้เจ้าของระบุ ID รุ่น ประเภท และ audience ใน catalog โดยระบุ executive สำหรับเอกสารลับ เก็บต้นฉบับที่ผ่านตรวจในที่จำกัดสิทธิ์ ไม่นำเอกสารบริษัทจริงเข้า Git นี้
2. ทดสอบชุดคำถามและ ACL ใน staging การอ่านไฟล์/OCR/vectorize ที่ล้มเหลวก่อน commit จะรักษารุ่นที่ให้บริการไว้ เจ้าของแก้เฉพาะหน้าที่ CLI แจ้งแล้วรันใหม่ สำหรับการถอนสิทธิ์เร่งด่วนให้ปิดเส้นทางหรือบัญชีที่ได้รับผลระหว่างแก้ไฟล์
3. เผยแพร่ด้วย `docker compose run --rm seed python -m knowledge ingest` จด revision จาก stdout พร้อมเลข change แล้วตรวจ /health/ready และรัน `scripts/check_live.py` ในสภาพแวดล้อมทดสอบ สูตรแคชใช้ revision จึงแยกคำตอบก่อนและหลังเปลี่ยนแปลง
4. ย้อนดัชนีด้วย `docker compose run --rm seed python -m knowledge activate REVISION` เมื่อ ACL รุ่นเดิมยังถูกต้องเท่านั้น หากต้องรักษาสิทธิ์ใหม่ ให้สร้างรุ่นใหม่จากเนื้อหาเดิมและ ACL ล่าสุด แยกการย้อนแอปโดย deploy Git commit/image ที่ผ่าน UAT
5. รัน `docker compose run --rm seed python -m knowledge prune` ทุกคืนผ่าน scheduler ขององค์กร อายุตามค่าเริ่มต้นคือ 30 วันสำหรับ traces และเคสที่ปิดแล้ว คำถามที่เปิดอยู่คงไว้จนปิดงาน แคชหมดอายุ 1 ชั่วโมง รุ่นดัชนีเก่ายังคงอยู่เพื่อ rollback ให้ DBA กำหนดอายุและลบตามนโยบายการเก็บรักษาก่อนใช้ข้อมูลจริง

## สำรองและกู้คืน

ใช้ `python scripts/backup.py` เพื่อสำรอง PostgreSQL ในรูปแบบ custom archive ลง `var/backups` และตรวจรายการใน archive เก็บไฟล์สำรองและ .env ในระบบสำรองที่เข้ารหัสแยกสิทธิ์ ผู้ดูแลควรเก็บ catalog, PDF, commit ของแอป, model revision และการตั้งค่า IdP แยกจาก DB ออกคีย์ใหม่หรือกู้คีย์ผู้ใช้ผ่านช่องทางลับ

กู้สู่ฐานข้อมูล **ใหม่** ที่สร้างจาก Postgres 16 และ pgvector รุ่นเดียวกัน สร้าง role `desk_owner` และ `desk_web` จาก secret store ก่อน ใช้ `pg_restore --exit-on-error -U desk_owner -d NEW_DATABASE BACKUP.dump` ตรวจจำนวน chunk, active revision, สิทธิ์ non-superuser และกฎ RLS แล้วรันชุดตรวจ end-to-end ก่อนสลับ DATABASE_URL เสนอ RPO 15 นาทีด้วย WAL archiving และ RTO 1 ชั่วโมง ให้ยืนยันทั้งสองค่าด้วย DR drill บนระบบลูกค้า

## การเชื่อมองค์กร

Compose เลือกโปรโตคอล llama.cpp สำหรับ Qwen ที่บริการ `llm` และใช้ Chat Completions กับ URL ภายนอก ถ้าชี้ Qwen รุ่นเดิมไปเครื่อง llama.cpp แยกให้ตั้ง `LLM_PROTOCOL=llama` และ `LLAMA_SLOTS` ตามจำนวนช่องจริง ถ้ามีเครื่องที่สองซึ่งใช้รุ่นโมเดล การตั้งค่า และสิทธิ์บริการเดียวกัน ให้กำหนด `LLAMA_EXTRA_URL` กับ `LLAMA_EXTRA_SLOTS` ทดสอบการเปลี่ยนเส้นทางด้วยชุดเฉลยและโหลดผสมก่อนรับงานจริง ใช้ `EVIDENCE_READER=off` เพื่อแยกผลของ reader ระหว่างวิเคราะห์

จดทะเบียน confidential web client ที่ IdP โดยใช้ redirect URI แบบตรงตัว `https://<portal-host>/auth/callback` เปิด Authorization Code พร้อม PKCE S256 และใส่กลุ่มที่ได้รับอนุญาตใน claim `groups` ของ ID token ระบบตรวจลายเซ็น issuer, audience, nonce, state และเวลา expiry ก่อนสร้างเซสชัน ระบุ `OIDC_SCOPES` ตาม IdP โดยต้องมี `openid` การเรียก API ผ่าน bearer token ใช้ issuer, JWKS และ audience ของ resource server แยกจาก web client ID

ตั้ง `PORTAL_ORIGIN` เป็น HTTPS origin ที่ gateway ให้บริการ ตั้ง `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `OIDC_JWKS_URL`, `OIDC_AUDIENCE` และ `OIDC_GROUP_EMPLOYEE/REVIEWER/EXECUTIVE` ตามค่าที่องค์กรออกให้ ส่ง `BROWSER_SIGNING_KEY` ที่สุ่มอย่างน้อย 32 ตัวอักษรค่าเดียวกันให้ API replicas ผ่าน secret manager ทุกเครื่องใช้ฐานเซสชันเดียวกัน ตั้ง `KNOWLEDGE_DATA_DIR` เป็นไดเรกทอรีที่เก็บ catalog และไฟล์เอกสารที่เจ้าของข้อมูลอนุมัติ เปิดด้วย `docker compose -f compose.yaml -f deploy/compose.enterprise.yaml --profile monitoring up --build -d` โปรไฟล์นี้บังคับปิดการยืนยันตัวตนผ่านบัญชีท้องถิ่น ให้ gateway proxy ทั้งหน้าเว็บ, /auth และ /api ไปต้นทางเดียวกัน และตั้ง access log ให้บันทึก path ของ callback โดยละ query string

เบราว์เซอร์เก็บ opaque session cookie แบบ HttpOnly/SameSite=Lax และ Secure บน HTTPS เซิร์ฟเวอร์บันทึกเฉพาะ digest ของ session ID เซสชัน SSO หมดอายุภายในหนึ่งชั่วโมงหรือก่อน ID token หมดอายุ สิทธิ์กลุ่มจาก IdP มีผลเมื่อออกเซสชันใหม่ หากต้องตัดสิทธิ์ทันที ให้ถอนที่ IdP แล้วรัน `docker compose run --rm --no-deps seed python -m knowledge revoke-sessions oidc/SUBJECT` การกดออกจากพอร์ทัลยกเลิกเซสชันของพอร์ทัล ส่วนอายุการล็อกอินที่ IdP อยู่ภายใต้นโยบายขององค์กร

สำหรับเครื่องภายในที่เปิด LOCAL_AUTH ผู้ดูแลออกคำเชิญให้บุคคลด้วย `docker compose run --rm --no-deps seed python -m knowledge issue-invite ACCOUNT ROLE` ส่งรหัสให้บุคคลนั้นผ่านช่องทางส่วนตัว ใช้ได้หนึ่งครั้งภายใน 10 นาที เซสชันท้องถิ่นนาน 8 ชั่วโมง และตรวจสถานะบัญชีทุกคำขอ บน Windows ตัวเปิด open-workspace.cmd ออกคำเชิญ employee ส่วน open-admin.cmd ออกคำเชิญ admin ในบัญชีแยกสำหรับผู้ที่มีสิทธิ์จัดการ Docker บนเครื่อง เมื่อย้ายจากระบบเดิม ให้ทบทวนคีย์เดิมที่มีอยู่ใน `var/compose/access.json` ก่อนถอนบัญชีที่เลิกใช้ การเปลี่ยนเวอร์ชันเก็บข้อมูลและคีย์ของผู้ใช้เดิมไว้

เจ้าหน้าที่กด **รับผิดชอบเคสนี้** ก่อนบันทึกผล ระบบบันทึกบัญชี เวลา และสถานะในธุรกรรมเดียว หากมีสองคนรับพร้อมกัน คนที่สองได้ HTTP 409 เจ้าของสามารถคืนงานเข้าคิว พนักงานติดตามผู้รับผิดชอบและประวัติการเปิด รับ คืน หรือปิดเคสได้ตามสิทธิ์ รายการเดิมที่ปิดก่อนอัปเกรดแสดงประวัติจากเวลาและชื่อผู้ปิดเดิม

เก็บ secrets ใน vault จำกัด network ระหว่าง API, DB และ LLM ตั้ง TLS, quotas, backups, central logging และผู้รับ alert ก่อนเปิดกลุ่มจริง ให้เจ้าของธุรกิจลงนามผล UAT แบบแยกความเสี่ยง พร้อมรายการข้อผิดพลาดคงค้างและวันทบทวนครั้งถัดไป
