# Architecture Design | Enterprise Knowledge & Support Agent

**ขอบเขตการให้บริการ** · พนักงาน 5,000 คน · 50,000 คำถามต่อวัน · ภาษาไทยและอังกฤษ

เจ้าของบริการคือทีม Knowledge Platform เจ้าของระเบียบคือฝ่ายบุคคลและการเงิน

## 1. เส้นทางข้อมูลและคำตอบ

**นำเข้า** เจ้าของเอกสารระบุไฟล์ ประเภท รุ่น และกลุ่มผู้อ่านใน catalog ระบบอ่าน PDF รายหน้า อ่านไฟล์แชตเป็นข้อความ และใช้ Tesseract ไทย/อังกฤษกับหน้าสแกนที่ไม่มีข้อความใช้ได้ หาก OCR ต่ำกว่าเกณฑ์ให้เจ้าของตรวจเฉพาะหน้าที่ระบุ ดัชนีรุ่นเดิมให้บริการต่อได้ การเผยแพร่รุ่นใหม่เปลี่ยนทั้งเวกเตอร์ ข้อความ และสิทธิ์ในธุรกรรมเดียว

**สอบถาม** แชตบันทึกข้อความตามบัญชีและบทบาท ตรวจขอบเขตและคำสั่งแทรกก่อนเรียกเครื่องมือ เมื่อตรวจสถานะเคส ระบบอ่านฐานงานตามเจ้าของโดยตรง คำถามระเบียบจะค้นใหม่ตามสิทธิ์ ใช้ชื่อเอกสารที่อ้างล่าสุดช่วยตีความคำถามต่อ คืนข้อความพร้อมรุ่นและหน้า หรือเปิดเคสให้เจ้าหน้าที่เมื่อหลักฐานไม่พอ

**ส่วนประกอบที่เลือก** โหมด API ใช้ embeddings ขนาด 384 มิติและ chat deployment ที่คืน JSON schema เช่น text-embedding-3-small และ GPT-4.1 mini ผ่าน gateway ที่องค์กรอนุมัติ PostgreSQL + pgvector เก็บดัชนีกับสิทธิ์ ดึงผู้สมัครสูงสุด 40 ส่วนแล้วจัดอันดับด้วย cosine และอักขระไทยสามตัว โมเดลเลือกหลักฐานหรือ NONE เซิร์ฟเวอร์คัดข้อความพร้อมวงเงินจากต้นฉบับ ประโยชน์คือขยาย inference ผ่าน quota ของ provider ได้ ส่วนต้นทุนขึ้นกับ token และเวลารอขึ้นกับเครือข่าย หากข้อมูลต้องอยู่ภายในองค์กร ยังมี E5-small และ Qwen2.5-1.5B Q4 สำหรับติดตั้งในเครือข่าย [การตั้งค่า API และการย้ายดัชนี](https://github.com/BeatChalongrat/test-LH-Bank/blob/main/docs/provider.md)

## 2. งบประมวลผลและเวลาตอบ

50,000 ครั้งเท่ากับเฉลี่ย 0.58 ครั้ง/วินาทีตลอดวัน หรือ 1.74 ครั้ง/วินาทีใน 8 ชั่วโมงทำการ สมมติช่วงพีก 10 เท่าของชั่วโมงทำการ จะต้องรับประมาณ **17.4 ครั้ง/วินาที** เริ่มด้วย API อย่างน้อย 2 replica หลัง TLS gateway และ DB แบบมี standby ให้ ingestion แยกจากเครื่อง inference ชุด Compose ที่ส่งมอบใช้วัด baseline แบบเครื่องเดียว

แคชคำตอบที่มีหลักฐาน 1 ชั่วโมง คีย์ประกอบด้วยคำถาม บทบาท รุ่นเอกสารและสิทธิ์ รุ่นกฎ โมเดล ปลายทางและ threshold บัญชีที่มีสิทธิ์รายคนหรือแผนกแยกคีย์ตาม subject การแก้สิทธิ์ เอกสาร หรือสมาชิกเปลี่ยน revision ทำให้แคชและประวัติสนทนาเดิมใช้ต่อไม่ได้ ระบบตรวจสิทธิ์ก่อนค้นและตรวจรุ่นอีกครั้งก่อนบันทึกคำตอบ

สมมติ hit 60% เหลืองานใหม่สูงสุด 20,000 ครั้ง/วัน ถ้าใช้ 600 input และ 16 output tokens ต่องาน คืองบ 12 ล้าน input และ 0.32 ล้าน output tokens/วัน บวก embedding สำหรับคำถามและเอกสาร คูณราคาต่อ token ของ deployment จริง ที่พีกมี cold path 7.2 ครั้ง/วินาที ต้องจองอย่างน้อย 432 requests/นาทีต่อ endpoint ก่อนเผื่อ ingestion และความผันผวน ปรับช่องพร้อมกันจาก throughput และ p95 ของ provider แล้ววัดซ้ำทั้งแชต

**ผลวัดแชต** เส้นทางโมเดลในเครื่องทดสอบ 30 นาที 18 ครั้ง/วินาที 32,400 คำขอจาก 5,000 บัญชี p95 9.74 วินาที ถูกพร้อมหลักฐาน 28,886 ข้อ โหมด API แยกคิว lookup และ chat จำกัดจำนวนที่รอ ปล่อยช่องก่อนบันทึก DB และเคารพ Retry-After เมื่อ chat provider ตอบ 429 ผลจาก HTTP fixture ใช้วัดคิวและเวลาฝั่งระบบ การเปิดจริงต้องวัด end-to-end บน deployment และ quota ขององค์กร [ผลทดสอบ](https://github.com/BeatChalongrat/test-LH-Bank/blob/main/evaluation/provider-capacity.md)

## 3. การประเมินและเกณฑ์เปิดใช้งาน

ให้ BU และเจ้าของระเบียบติดป้ายคำตอบ ข้อเท็จจริง เอกสารที่เกี่ยวข้อง บทบาท และกรณีที่ควรส่งต่อ แยกชุดปรับ threshold ออกจากชุดตรวจรับด้วยหัวข้อ/เวลา สุ่มคำถามจริงที่ลบข้อมูลส่วนบุคคลทุกสัปดาห์ แบ่งตามฝ่าย ความเสี่ยง คำผิด และรุ่นเอกสาร ใช้ผู้ตรวจสองคนตัดสินกรณีไม่ตรงกัน

| ตัวชี้วัด | วิธีวัดและการตัดสินใจ |
|---|---|
| Accuracy และ coverage | คำตอบหรือการส่งต่อที่ตรงเฉลย ÷ ทั้งหมด รายงานความถูกต้องเฉพาะคำตอบอัตโนมัติและสัดส่วนที่ตอบได้เพิ่มเติม เพื่อจับการส่งต่อมากเกินไป |
| Hallucination rate | คำตอบอัตโนมัติที่มีอย่างน้อยหนึ่งข้ออ้างซึ่งหลักฐานไม่รองรับ ÷ คำตอบอัตโนมัติที่ตรวจ เจ้าของเนื้อหาตรวจความหมายและเงื่อนไข การคัดข้อความตรงยังอาจเลือกผิดบริบท |
| Retrieval P@k / R@k | ต่อคำถาม วัดเอกสารที่เกี่ยวข้องในผลค้น ÷ จำนวนที่คืนภายใน k และ ÷ จำนวนเอกสารอ้างอิงทั้งหมดที่ผู้ใช้นั้นมีสิทธิ์ ตามลำดับ แล้วเฉลี่ยข้ามคำถาม รายงานที่ k=1,3 และแยกเคสที่ไม่มีคำตอบ |

เสนอเกณฑ์ UAT เบื้องต้นสำหรับงานทั่วไป accuracy ≥95%, coverage ≥70%, hallucination ≤1%, recall@3 ≥95% พร้อมช่วงความเชื่อมั่น 95% ชุดทดสอบสิทธิ์ต้องไม่มีข้อมูลข้ามกลุ่ม และงานมีผลจ่ายเงินจริงต้องมีผู้อนุมัติ ทดสอบโหลดผสมจริงที่ 18 ครั้ง/วินาที 30 นาที โดยตั้งเป้า p95 แคช ≤250 ms, cold ≤3 s, HTTP 5xx <0.5% ค่าทั้งหมดเป็นเป้าหมายสำหรับตกลงกับ BU

## 4. สิทธิ์ เหตุขัดข้อง และการส่งมอบ D2

ตรวจลายเซ็น issuer, audience, อายุ และกลุ่มจาก IdP แล้วผูกบทบาทกับ subject ฝั่งเซิร์ฟเวอร์ PostgreSQL RLS กรองบทบาท แผนก และรายคนก่อนค้นและดาวน์โหลด เอกสารเงินเดือนตัวอย่างเปิดให้ executive ส่วน admin จัดการสิทธิ์ได้ การส่งต่อบันทึกชุดเอกสารจำกัดสิทธิ์ของผู้ถาม แล้วตรวจสิทธิ์เจ้าหน้าที่ซ้ำทั้งในคิว ประวัติเคส และก่อนรับหรือปิดงาน [PostgreSQL RLS](https://www.postgresql.org/docs/16/ddl-rowsecurity.html)

แยกโมดูล ingestion, retrieval, inference, identity, agent และ HTTP ผูก trace ID กับเหตุผลที่ตอบ/ส่งต่อ รุ่นเอกสาร รหัสหลักฐาน และเวลาค้น/สร้าง เก็บคำถามที่ปกปิดอีเมลและเลขบางประเภทในคิวจำกัดสิทธิ์ D2 รับสัญญาณจาก metrics และ JSON log ตั้งเตือนเมื่อ provider error >2% ใน 5 นาที หรือ p95 เกิน SLO 10 นาที ตรวจคิวค้างข้ามวัน ให้ HR/Finance รับเคสตามเจ้าของข้อมูล

ก่อนเปิดพนักงานทั้งองค์กร ให้เชื่อม SSO/TLS และระบบแจ้งเตือนของลูกค้า ทดสอบ restore จาก backup และโหลดแบบ cold/mixed เริ่ม canary 5% ตรวจคุณภาพตามรุ่น หากเปิดเผยข้อมูลผิดสิทธิ์ให้หยุด route ทันที กรณีคุณภาพถดถอยให้ย้อนรุ่นดัชนี/แอปที่ผ่าน UAT หลังตรวจ ACL ปัจจุบัน ทีม D2 ได้คำสั่งสืบ trace เล่นเคสซ้ำ ปิดรายการ และกู้ระบบใน [คู่มือปฏิบัติการ](operations.md)
